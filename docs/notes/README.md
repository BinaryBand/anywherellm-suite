## Layout and build

- **`docs/browser-tab.md` and `docs/fence-lean.md` are the file formats the phone app and the bridge read, and `tools/versions.env` is the image every check and the test lab use: data, not a package.** The phone app's bridge is its own repository (`~/dev/anywherellm-bridge`); it and the suite share only the fence's file contract, no code.
- **One toolchain for the JavaScript parts,** at `packages/`: one `package.json`, `tsconfig.json`, lock and `build.mjs`, no npm workspaces. Node runs `.ts` itself (type stripping), so there is no `tsx`; `erasableSyntaxOnly` keeps the source strippable. The dev tools are `typescript`, `esbuild` and `@types/node@18`; the only other dependencies are the vendored libraries below.
- **Node 22.18+ to develop, Node 18 for what ships.** The image's Node is 18, so everything AnythingLLM runs, and the installer, targets `node18`. The API floor is Node 18's: `AbortSignal.any` (20.3) is out, and `target: node18` doesn't catch it.
- **ESM is chosen by extension.** `packages/package.json` has no `"type"`, so `.js` and `.ts` are CommonJS, which the skills need (AnythingLLM `require`s them); whatever is ESM is `.mts` (shared helpers, tests and the installer) or `.mjs` (`build.mjs`). A `"type": "module"` anywhere above a skill, or in a nested `package.json`, breaks the CommonJS fixtures.
- **Parts share the contract and the tooling, never modules.** `packages/shared/` is dependency-free source that esbuild bundles into each part (`#shared/...`, mapped by `package.json`'s `imports`), so a fix in it reaches a part only when that part is rebuilt. `build.mjs` fails a bundle that takes in a file from outside its own `src/` and `shared/`. The installer carries the control server and the skills as built text, not as imports.
- **Vendored dependencies are named.** `build.mjs`'s `VENDORED` lists what a part may bundle, pinned exactly in `package.json`: QuickJS for the library, `puppeteer-core` for the browser (the newest that runs on Node 18), `fast-json-patch` for apps. "No dependencies shipped" means nothing is installed beside a part. `STUBBED` bundles Puppeteer's browser-download, proxy, archive and BiDi modules as empty ones, which is most of its size; a pattern that matches nothing fails the build, so an update that moves a module is caught.
- **A skill's `static/` is text inlined into its `handler.js`** (`STATIC_FILES`), because the Hub's upload and install's payload take text. A file at the same path under `<storage>/<hubId>/static/` wins at run time, so guides, snippets, parts and pages can be tuned on the live instance and a reinstall doesn't undo it. Only text and code that runs inside QuickJS or a page is static; what touches secrets or the network stays in TypeScript.
- **Skill tests run against the built bundle** (what AnythingLLM loads); a test that imports `src` directly uses `.ts` import paths. `tools/check` builds once and runs each part's `<part>:unit`. Fixtures and e2e scripts stay `.js`: they stand in for, or run inside, AnythingLLM's own JavaScript.
- **Checks.** `lefthook.yml` calls the scripts in `tools/`, and `make` only wraps them. CI runs the type-check, the tests and `tools/e2e` on Linux, the one platform tested; `tools/e2e` and `tools/e2e-skill` need a container and are not hooks. `tools/versions.env` pins the one AnythingLLM image every check uses. Mode-600 checks are skipped on Windows, which has no modes (the code and these checks stay for whoever runs it there).
- **Evals live in `~/dev/test-lab`:** they are slow, cost model calls and vary between runs. It installs a suite commit with that commit's `tools/install`, from a worktree, so `main` can move during a run.

## What AnythingLLM gives us

- **A stdio MCP server gets AnythingLLM's own environment** (`server/utils/MCP/hypervisor`): `AUTH_TOKEN`, `SERVER_PORT` and `STORAGE_DIR` reach an MCP server in a container and on Desktop alike (the bridge's control server uses them), so the servers file (`plugins/anythingllm_mcp_servers.json`) holds no secret. AnythingLLM listens on `SERVER_PORT`, else 3001. An entry is `command`/`args`/`env`, or `url` with `type` `sse`, `streamable` or `http` (`streamableHttp` is refused); single tools can be switched off with `anythingllm.suppressedTools`.
- **Desktop has no password or multi-user mode,** and only Linux with podman has run on real hardware (the root README's table says the rest).
- **A skill's `handler.js` is loaded afresh for each agent run,** so state that must outlive a call is kept on `globalThis` (`perProcess`), and a cache that depends on the build goes through `perBuild`.
- **A skill has no time limit.** A scheduled job has one (`SCHEDULED_JOB_TIMEOUT_MS`, AnythingLLM's 5 minutes by default), runs in a child AnythingLLM forks with no workspace, only the tools it names and approval granted, and names a skill `@@<hubId>` (an MCP server `@@mcp_<name>`), which is why the bridge's control server's `schedule` takes `@` in a tool id. `jobTimeLeft()` is that child's own budget. The built-in `create-scheduled-job` tool asks the user's approval in the chat and works in single-user mode only.
- **AnythingLLM keeps a skill's settings and on/off switch in its `plugin.json`** and writes it again when a setting changes, so install keeps `active`, each `setup_args` value and the description's `Saved now:` part when it updates a skill, and `health` compares JSON by value.
- **Internals are a last resort:** supported surfaces first. What the pages still lean on is the public folder they are served from and the collector's `custom-documents/raw-*.json` files their events are read from.

## Installer

- **The agent's control server is anywherellm-bridge's** (moved 2026-10-20; its notes have why, and the decisions that came with it: no MCP SDK, roles, the runtime, install being polite to the servers file). The suite's `install` therefore writes the skills only, and no servers-file entry.
- **`Told` is the one error to show as it is** (`#shared/errors`): a skill's own refusals and the installer's extend it, so a catch tells them from a bug.
- **The installer remembers nothing.** `--storage DIR` on every command, else Desktop's, else refuse: with one instance to install into, remembering earned less than a settings file costs. `uninstall` never removes a skill's data.
- **The pages' key comes from install** (`--page-key brx-...`): one browser-extension key made by the user serves every skill's pages. Skills used to make their own through AnythingLLM's model, an internal. The cost is a setup step, and a revoked key stays broken until install is given another. It isn't moved to `/api/v1`, whose upload takes only a developer key, which can do everything and can't sit in a public page.

## Shared infrastructure

- **The fence** (`shared/fence.mts`, `net.mts`): a skill reaches the public web only. Private ranges are one `net.BlockList`; a request is checked at the skill's own lookup and again for each redirect hop, and connections are pooled a few seconds per allow-list. The user's own network is let through by `FENCE_ALLOW` (hand-written hosts, any port) or by an ask.
- **Fence asks** (file contract: [docs/fence-lean.md](../fence-lean.md)). A skill that meets a refused origin in a chat AnywhereLLM streams waits for the user's once, always or deny, written by the bridge; an unanswered ask is denied. AnythingLLM's own `requestToolApproval` can't ask through the developer API (without Telegram it denies), which is why this exists. Scheduled jobs, Telegram and the web UI never ask and are refused.
  - **A yes lets one origin through** (scheme, host and port), never the host's other ports: approving a service on one port had let every skill reach AnythingLLM and the bridge on the same name. A key goes over plain http only to a `FENCE_ALLOW` host or an origin let through always. A browser page's own requests never ask and inherit the workspace's latest run's grants for 2 minutes after its last call, since a page loads between calls.
  - **The run scope is ambient, not a parameter at each call site:** each skill's handler runs its call in one `AsyncLocalStorage` run (`runAs`); a refused request asks (`withAsk`) and is sent again; a library function's run reaches what the run that started it was let through but never asks; work that outlives a call (the browser's launch and timers, the device sign-in poller) starts `outsideRun`.
  - **Caches depend on the build:** a reinstall once left a running AnythingLLM reading the hosts' entry an earlier build kept under the same `perProcess` key, so every fenced library call failed until the file changed. A cache now goes through `perBuild`, keyed by `SHARED_STAMP` (a hash of `shared/`'s sources); `perProcess` is for what holds something live (a browser, a timer, a queue).
  - **A no is final in words** (`the user declined it` or `didn't answer in time`, then `FENCED`'s "That's final"), so the agent doesn't try another way.
- **Atomic files** (`shared/atomic.mts`): a write goes to a temp file and renames; `updateJson` takes a lock folder beside the file across processes (a scheduled job is a process of its own), re-reads inside it and breaks a stale lock. `readJson` takes only a missing file for empty, so a damaged file is never written over.
- **The vault** (`shared/vault.mts`, `logins.mts`) is one encrypted file for the instance, `<storage>/vault-lean/vault.json`, changed under that lock. Work that needs the network (a token's renewal) is done before the change, which checks that what it read is still there. A test with two processes writing at once loses nothing and fails without the lock.
  - **The key** is derived from AnythingLLM's `SIG_KEY` and `SIG_SALT`, which sit in the `.env` in the same storage, so a copy of the storage could open the vault. `VAULT_KEY_FILE` moves it outside (setup in the root README's [Secrets](../../README.md#secrets)); it belongs in AnythingLLM's environment, not its `.env`, which AnythingLLM writes again with only the keys it knows. The HKDF label (`INFO` in `vault.mts`) must never change: it would change every derived key.
  - **Cookies are a sealed file per workspace** beside the vault (`vault-lean/sealed/`), so a cookie save rewrites neither the vault nor every process's cached copy.
  - **Not a security boundary:** the skills run in AnythingLLM's process and open the vault with the same key. A stronger step needs an OS boundary, a container.
- **The Vault page** (`shared/vault-page.mts`, `vault.html`) is shared code each skill that keeps secrets bundles, so each stands alone. A Vault skill of its own and merging library with browser were both set aside: a skill can't call another, the browser needs a Chrome and the library doesn't, and one tool of about 20 actions routes worse than two. Each skill writes and applies only its own section (logins, keys); the page shows a tab for each it finds, and a module `VERSION` stops an older skill writing over a newer page.
  - **Open:** the tab state carries the Vault's link (`docs/browser-tab.md`), so anyone with a tab's link reaches the Vault; and the library's page watch stops 30 minutes after the page was shown, so a delete on a Vault opened later waits for the next library call.
- **Pages** (`shared/pages.mts`): a skill's pages go into AnythingLLM's public folder, served without a sign-in. A page posts what the user does through the browser-extension upload with the `brx-` key, which can add and embed documents, list workspaces and revoke itself, never read a chat or a document. The collector writes each post to a file the skill takes oldest first, claimed by renaming, so only one process applies an event. Posts are applied while a page is open and drained before every call, in turns per event title, so a call reads a page after what was posted; the agent learns what the user did from its next read, not from a queue of notes, which any context could consume. A page's link is a capability URL carrying a secret its events repeat; `rotate` removes the old files.
  - **A public path can't leave the public folder** (`publicPath`), and every write, removal, listing and rename there goes through it. No posted value is turned into a path: an earlier `oauth-code` event, taken without a secret because the provider's redirect page had none, once let anyone with the pages' key remove any file AnythingLLM could write, the vault included. That flow is gone (see Library).
- **Text the agent reads is data, never instructions.** `shared/answer.mts` checks the requests the agent writes (it never sets a credential header; a key goes in from the vault), hides every secret in what comes back, and clips long answers, giving a long JSON answer its outline.
- **Same-origin pages, recorded, not fixed.** Every page is model-written script served on AnythingLLM's own origin, so in a browser signed in to AnythingLLM it could read the web UI's token and call its API. The fix is a trusted shell holding the page in a sandboxed iframe, posting and polling over `postMessage`.

## Library

Why QuickJS, what was measured and the limits: [skills/library](skills/library/README.md).

- **The sandbox contract:** a function runs in QuickJS (WebAssembly) in AnythingLLM's process and sees its input and `kit`, never a file, a key or AnythingLLM. `kit.http` reaches only its toolkit's hosts, through the fence, with the toolkit's keys added outside the script and hidden everywhere; `kit.run` runs a flow and shares the run's deadline, request budget and log; `kit.state` is kept when a run ends well. The sandbox goes no further once the deadline or a stop has decided a run.
- **`policy.ts`'s `check` is the one place to refuse:** when a function is saved, a run starts and each request is made, from a function or the agent's own `call`. It allows everything while the user tests; approval and read-only keys would go there.
- **Secrets are given on the Vault page only, never on AnythingLLM's question card:** once answered, the card shows the answer as plain text in the live chat whatever its `inputType`. The page's fields ask for a new password (`autocomplete="new-password"`, random names) so Chrome fills in no saved login, and what's typed is sealed on the device with the vault's public key. A key is limited to 60 calls a minute, per process (`credentialed`). A toolkit keeps only its extra hosts; the base address's are derived, so changing a base address doesn't leave the old host reachable.
- **The description lists what is saved** (`listing.ts`, refreshed after `save`): a model that can't see the library's contents goes to a web search, and AnythingLLM reads `plugin.json` again for each agent run.
- **Runs outlive the chat.** A chat waits `LIBRARY_WAIT_MS`, then answers with the run's id and leaves it going in AnythingLLM's process (up to `LIBRARY_RUN_MS`); `run_id` waits again and `stop` stops it. Each run is a file of its own, `running` at its start and `interrupted` once its process is gone or it is a minute past its deadline. The end is pushed through AnythingLLM's web push and leads the next `library` or `run` answer, tracked by one `unseen/` marker per run so a chat and a job never write the same file; a job's run that fails keeps its marker for the next chat.
- **A scheduled job never goes to the background:** it gets the job's time left less a margin for the agent's report, and a run is refused when too little is left. Scheduling is AnythingLLM's own `create-scheduled-job` with `tools: ["@@library-lean"]` (guide topic `schedules`).
- **The only sign-in is GitHub's, by the device flow** (`presets.ts`, `device.ts`): the suite's own public client, no redirect, no secret, and nothing the agent writes but the scopes. Any other service takes a key or a token on the Vault. Sign-ins with a client of the user's own (a redirect page, PKCE, and a definition the agent writes from a provider's docs, which a page it read may steer) were the heaviest and most exposed code in the skill, with four security fixes in a day; they are on `archive/generic-oauth`.
  - **A waiting code lives on its vault entry,** not in the process that started it, so whichever process asks next finishes it once, under the vault's lock.
  - **A refresh token is spent once** for a provider whose tokens expire: requests that find a token running out wait on one renewal, made outside the lock and kept only if the entry still holds the refresh token it used. GitHub's don't expire.

## Browser

Details: [skills/browser](skills/browser/README.md).

- **The skill decides what the model can't see:** a field behind a dialog, a date field's format, a submit the page keeps disabled and a code field that moved are handled in code, and it refuses what wouldn't work and says why. Secrets are entered on the tab's page only, sealed, and typed or set by the skill; the model never sees them.
- **A saved password is set, not typed** (`act.ts` `fillOn`): one call into the page checks that the field's window is the top one and is on the login's host, then sets the value through the input's own setter, since keystrokes go to whatever has the focus, which a page can move between keys. A code is typed after the same check. A page that ignores a set value is refused, and the user takes the tab over. The tab's picture hides a shown password: the read that marks a password field also gives it `-webkit-text-security: disc` for good.
- **A takeover is one hold:** the agent reads but `open`, `act`, `login` and `call` are refused, through one dispatcher check that also marks the tab busy, so a user's tap and an agent step never drive the tab together. A login saved, a password typed while holding and a passkey a site made then are all an `Offer`, saved once the page no longer asks for a password and is still on its site.
- **Passkeys:** every tab has Chrome's virtual authenticator holding the saved passkeys. Only the user adds one, while holding the tab; one made while the agent has it is taken out. Nothing else may connect to the skill's Chrome during a passkey case: even one DevTools message leaves the authenticator unanswered.
- **Cookies** are saved through the browser's own DevTools session after a step and as it closes, only when they changed. localStorage and IndexedDB aren't kept: a site that keeps its sign-in there signs in again with the saved login. Chrome's profile is a temporary folder removed in the background and with retries, because a throw from that handler would take AnythingLLM down.
- **Choices from the eval.** A check that a person is at the browser is the user's: act refuses to click one by its own name, and real reCAPTCHA, hCaptcha and Turnstile sit in cross-origin frames a read never sees, so the guide covers those. An identity provider's Allow for the asked sign-in is the agent's to press.

## Apps

Details: [skills/apps](skills/apps/README.md).

- **hubId `apps-lean`,** ported from the lean edition (not the unmerged `apps-manager` branch), on the shared helpers: a lock per app, the invocation's workspace, and the pages' key, public folder, event intake and folder watch. Its parts, topics and runtime are `static/`, tunable under `apps-lean/.static/` (a dot, so no workspace can be named like it).
- **A page's events reach only its own app:** each app has a secret in its page, and an event is applied only to the app whose secret it carries. The lean edition took the workspace and app an event named, so one page's link could change any workspace's apps.
- **The page check runs in a worker thread** the call waits for, up to `CHECK_ALL_MS`: a vm timeout that cuts into a microtask corrupts Node's async hooks, which ends a process, while in a worker it ends only the worker. Node's vm is no security boundary; `page.html` is the model's own.
- **A scheduled job may name a workspace** (the first skill to take one from the model) but is held to `list`, `read` and `do` on an app whose app.json says `"jobs": true`, which only a chat's `edit` sets; `delete` is refused in a job.

## Notebook and archived skills

- **Notebook** (`packages/skills/notebook`) is leaner than the memory skill on purpose: no embedder or vectors (a paraphrase can miss; the agent can try other words), no scopes, no two-call `apply`. If agents don't think to read it, the first thing to try is listing notes in the skill's description, as the library lists its functions.
- **Archived, not shipped:** the memory skill (it wrote into AnythingLLM's vector database through server modules, no real agent had called it, and AnythingLLM 1.16 has memory of its own) and the SSH targets. If memory comes back: its facts in its own file, its vectors in a file of its own, embeddings from `POST /v1/openai/embeddings`, keyword search when no key is set. `install` doesn't remove a skill it no longer carries, and the live instance keeps its `memory-lean/` data.

## House rules

- **No migration shims.** Code that only carries an earlier edition's data or config over is not kept: the only installed instance is the author's and is migrated once, by hand or by an uncommitted script, and the code then knows the new format only. A later user with older data would be given a one-off script outside the packages.
- **The name is AnywhereLLM Suite,** so it isn't mistaken for Mintplex Labs' AnythingLLM on sign-in consent screens and public pages. Names that refer to AnythingLLM itself (`ANYTHINGLLM_*`, `anythingllm_mcp_servers.json`), the skills' hubIds and folders (`*-lean`) and the vault's HKDF label are unchanged. No aliases for old names.
- **Linux is what's supported; Windows and macOS are nice to have.** CI, the "verified" claims and the installer's docs cover Linux only, and nothing is promised elsewhere. But don't cut those machines off on purpose or without reason: reach for generic, platform-agnostic tools (TypeScript and Node's own APIs, `path`, no shell-only or Linux-only tricks in `packages/`), keep the small platform branches that exist (`install/src/paths.mts`'s Desktop folders, `shared/atomic.mts`'s Windows lock retries) rather than deleting them, and add a Linux-only dependency only when it buys something real. If a Windows or macOS machine turns up that needs fixing, a fix is welcome; adding it back to CI is a decision of its own.
