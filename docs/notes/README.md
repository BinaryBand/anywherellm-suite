# Notes

Repo-wide decisions and their reasons. A part's own notes live beside this file, under `docs/notes/<group>/<part>/`: [skills/library](skills/library/README.md), [skills/browser](skills/browser/README.md) and [skills/apps](skills/apps/README.md). The memory skill's notes went with it to the branch `archive/memory-skill`.

## Layout, 2026-10-15

- `packages/` holds what runs beside or inside AnythingLLM (bridge, mcp, skills). `app/` is the phone client and sits outside it. `contract/` is shared data, not a package.
- The Python parts form a uv workspace (one lock, shared ruff rules), and the JavaScript parts one `package.json` (one install); each part stays a separate distribution. Sharing tooling is allowed; sharing modules is not.
- Each skill ships as its own zip, so a skill is the package, and `packages/skills/` only groups them.
- No `.github/`. The gate is `lefthook.yml` calling the scripts in `tools/`, so the root gets one file and no hooks folder, and local and any later CI run the same scripts. The cost: nothing tests Windows or macOS (the mcp deploy's native mode, and the launchd and Task Scheduler managers the Python bridge had), a hook can be skipped with `--no-verify`, and there is no clean-room run. A hosted workflow can come back for the OS matrix alone. *(It did: see "The bridge's service on each OS, and CI" below.)*
- Parts are named by role. The bridge was `anythingllm-toolkit` and is now `anythingllm-bridge` (see the bridge section below).

## TypeScript under packages/skills, 2026-10-15

- **One config, at `packages/`** (first at `packages/skills/`): `tsconfig.json` beside `package.json`; the repository root has neither, because it is Python and Flutter. It includes every skill's `src` and tests and `shared/` by glob, so a new skill needs no config of its own.
- **`packages/shared/` holds helpers, and a part's output still stands alone.** A skill or the bridge imports `#shared/...`, which `package.json`'s `imports` field maps to `shared/*.mts`; Node, `tsc` and `esbuild` all resolve it, so tests, the type-check and the bundle use one mechanism (a `paths` alias would be invisible to Node). `esbuild` bundles the helper into the skill's `handler.js`, which then requires only Node built-ins; `tsc` alone would leave the import in the output. This relaxes the old rule "nothing a part ships imports from outside it": `shared/` is dependency-free source copied in at build, never a runtime import, so a fix in it reaches a part only when that part is rebuilt. First helper: `writeAtomic`, which was written separately in `apps`, `browser` and `memory`, and by hand in the bridge's `saveEnv`; it moved from `skills/shared/` to `packages/shared/` when the bridge became its second user, and `build.mjs` allows `shared/` for both parts.
- **Node 22.18+ to develop, Node 18 for the shipped code.** Node runs `.ts` itself (type stripping), so there is no `tsx`; `typescript`, `esbuild` and `@types/node@18` are the only dev dependencies, the last so that a newer API fails the type-check. Skills bundle with `--target=node18`, the bridge with `node20`. `erasableSyntaxOnly` keeps the source strippable (no enums); TypeScript 7 dropped `moduleResolution: node`, so the config uses `module: preserve` with `bundler`.
- **ESM is chosen by extension, not by a `package.json`.** `packages/package.json` has no `"type"`, so `.js` and `.ts` are CommonJS, which the skills need (AnythingLLM `require`s them, and the CommonJS fixtures and the built `handler.js` sit under it). Whatever is ESM is `.mts` (the shared helper, the tests, the bridge's source) or `.mjs` (`build.mjs`). A `"type": "module"` anywhere above a skill would break it; in a nested `package.json` it also turned the CommonJS fixtures into ESM. (Earlier there were nested `package.json` files for this; renaming to `.mts` removed them.)
- **What a skill ships beyond `handler.js` and `plugin.json`** goes in its `static/` folder, which `build.mjs` inlines as `STATIC_FILES` (text only: the Hub's upload and install's payload take text).

## The bridge, rewritten in TypeScript, 2026-10-15

- **From `anythingllm-toolkit` (Python), keeping its behaviour on the wire:** the routes, the allowlist's rules, the `{"error": ...}` shapes and statuses, the 120 s timeout, the key check's cache (60 s good, 10 s refused), the login that is read afresh and retried after a 401. The layers (`cli`, `api`, `adapters`, `core`) and their `Protocol` ports became nine flat files, because a function argument is enough to put a fake in at that size.
- **Renamed to `bridge` throughout.** The command is `anythingllm-bridge`, the file `bridge.env` in `~/.config/anythingllm-bridge/`, the port `BRIDGE_PORT`, `/health` says `"service": "anythingllm-bridge"`. `TOOLKIT_DATA` and `TOOLKIT_SERVICE` went with the venv and the service managers. **Two names are not changed yet and are the app's and the MCP servers' to follow:** the pairing link's `toolkit=` field (AnywhereLLM Lite reads it by that name), and what `packages/mcp` reads (`ANYTHINGLLM_TOOLKIT_URL`, `~/.config/anythingllm-toolkit/toolkit.env`, the `toolkit_client` package). The bridge writes `ANYTHINGLLM_BRIDGE_URL` into the servers' env files, so the MCP servers do not find it until they are moved in and renamed to match. Change them together. *(Done for the MCP side: see "The control server" below. The pairing link's `toolkit=` field is still the app's.)*
- **One file, no dependencies:** `node:http`, `fetch` and `util.parseArgs` replace FastAPI, httpx and Typer. The artifact is `dist/anythingllm-bridge.cjs`, with the default allowlist from `contract/default-allow.txt` inlined by esbuild. It is `.cjs` so that a fixed extension makes the file run the same wherever it is copied (`.mjs` would do as well; nothing needs CommonJS here, unlike the skills, which AnythingLLM `require`s). The target is Node 20, the system's.
- **Left out on purpose:** the launchd and Windows Task Scheduler managers (never run on real hardware), the venv building (there is no Python), `--container` discovery through podman or docker (`install --storage` only), the QR code (`pair` prints the link), `routes`, `logs`, the migration from earlier default allowlists (nothing is installed to migrate). `health` keeps the checks that still apply.
- **Tests import `src/` directly** (Node strips the types) and run the real server against a fake AnythingLLM on a port of its own, so one test covers login, key check, allowlist, forwarding and error shapes together. `bundle.test.mts` runs the built file. Not covered: a real `systemctl` (`service.test.mts` scripts it) and a real AnythingLLM.
- **One `package.json`, one `tsconfig.json` and one `build.mjs` for the JavaScript parts, at `packages/`.** `package.json` holds the toolchain (`typescript`, `esbuild`, `@types/node`), the scripts (`typecheck`, `bridge:test`, `skills:test`) and the `#shared/*` imports map; `shared:test` runs the helper's tests and `build.test.mts` (the boundary check), and `tools/check` runs it before either part's tests; there is one `node_modules/` and one lock, and the repository root gained nothing. There are no npm workspaces: nothing a part ships has a dependency. There is no `package.json` in `bridge/` or `skills/`; module types follow the extension (see above). The type-check covers both parts in one run, so `tools/check bridge` also type-checks the skills and the reverse, and the bridge is checked against Node 18's types (`@types/node` is pinned for the skills; the bridge targets Node 20 and uses nothing newer). `packages/mcp` is Python and not part of it. `tools/boundaries` lost its two ast-grep rules, which compared two Python packages. What remains of the rule "no part imports another": `build.mjs` fails a bundle that took in a file from outside its part (the bridge's `src/`, `shared/` and the contract; a skill's `src/` and `shared/`), the app is grepped, and a Python part cannot import a TypeScript one. A type-only import or one in a test is erased or not bundled, so the build check does not see it; a grep rule like the app's would.

## Follow-ups to the bridge, 2026-10-15

- **The boundary check has a test** (`packages/build.test.mts`): a bundle that takes in a file outside its allowed prefixes fails and leaves no output, `clean` is what is removed, and a prefix is a folder (`a/src-old/` is not `a/src/`). `build.mjs` exports `bundle()` and runs the builds only as the entry script.
- **A client that leaves ends the upstream call.** The server aborts a controller when the response closes unfinished, and `Upstream.exchange` passes the signal to `fetch` (with the timeout, through `AbortSignal.any`, Node 20.3+). The shared login and key check get no signal, since other callers wait on them. An aborted call is an `AbortError`, not a 502, and is not retried; it is logged as `client closed`. A POST may already have taken effect upstream, as with any dropped connection.
- **`service.usable` asks the manager, not the machine:** `systemctl --user is-system-running` answering running, degraded or starting, through the injected `Run`. That made the start path testable (`service.test.mts`) and changed one behaviour: a host with systemd but no user session bus (ssh without lingering) now gets the "run `serve` under your own supervisor" hint instead of a failing `enable`. `uninstall` and `health` key on the unit file existing, not on the manager answering: `uninstall` tries `disable --now` whenever `install` defined a unit and says so when systemctl refuses. The bridge needs Node 20.3 for `AbortSignal.any` (the README and `build.mjs` say so; nothing checks it at start).
- **Still not run:** a real `systemctl` and a real AnythingLLM.

## A server that calls the bridge: world_mcp, 2026-10-15

- **One tool, `world_workspaces`, one route (`GET /workspaces`),** to test a server's calls to the bridge with the least code. `build_server` takes an `httpx.AsyncClient` already pointed at the bridge and carrying the key, so a test puts in a mock transport and `__main__` puts in the real one; there is no client class, port or settings type yet. `httpx` is now a direct dependency (the `mcp` SDK already pulled it in).
- **Three layers of test:** the mock-transport tests for the request and each refusal; a **contract test** that the route is in `contract/default-allow.txt`, using a small copy of the bridge's matching rules (`allow.mts`: no method means GET, POST, PUT or DELETE, whole segments, `*` for one) with its own test so it cannot pass vacuously; and a stdio test against a stand-in bridge over real HTTP. The copy of the matching rules is the price of Python not importing TypeScript; if `allow.mts` changes how a rule reads, `test_the_allow_check_would_catch_a_route_the_list_lacks` is the place to follow.
- **Errors:** the bridge's refusal is passed to the agent as it was said (`the bridge answered 403: the bridge doesn't pass ...`), and an unreachable bridge is said so. No error classes: one `ToolError` with a message.
- **Not tried:** the real bridge in front of a real AnythingLLM. The bridge's own tests run it against a fake AnythingLLM in Node; this part's tests stand in for the bridge.

## tools/e2e: the servers against a real AnythingLLM and the real bridge, 2026-10-15

- **What it starts:** a container of the pinned image on a free port (password and JWT secret passed as `-e`, no bind mount), the bridge built from `packages/bridge` on another with the default `BRIDGE_ALLOW`, a developer key made through the same login the settings page uses, and a workspace made with that key. It then runs `packages/mcp/e2e` with `E2E_BRIDGE_URL`, `E2E_DEVELOPER_KEY` and `E2E_WORKSPACE`. Run by hand first (the same steps), then scripted.
- **No bind mount, on purpose:** with a mounted storage folder, rootless podman leaves it owned by a sub-uid that the user cannot delete without `podman unshare`, and the bridge would not be able to read AnythingLLM's `.env`. The bridge gets the password from an `.env` of its own in the temporary folder (`ANYTHINGLLM_ENV`), which is also why nothing is kept: stopping the `--rm` container removes its storage.
- **Never touches what is running:** free ports, a container named for the script's pid, a settings file for the bridge (`BRIDGE_ENV_FILE`) and a `MCP_ENV_DIR` inside the temporary folder, so `~/.config` is not read or written. The trap kills the bridge by pid (an earlier `pkill -f` matched its own shell) and was checked on success, on a failing test and on SIGTERM.
- **Not a hook:** it needs a container engine and an image, so it is `make e2e` and not in `lefthook.yml` or `tools/check`. The first run pulls the image.
- **What it found:** nothing the mock-based tests had wrong on `GET /workspaces`; the bridge's 401 and 403 are as `contract/endpoints.md` and the bridge README say. One rough edge: a refusal reaches the agent with the bridge's raw `{"error": ...}` in it.
- **Not covered yet:** routes other than `GET /workspaces`. The chat and schedule routes in `default-allow.txt` come with the servers that call them. *(Done: see "The control server" below.)*

## The control server: chat and schedule as roles of one MCP server, 2026-10-15

- **Reverses an earlier layering.** `anythingllm-mcp` kept `chat_mcp` and `schedule_mcp` as two servers over a shared `toolkit_client`, with import-linter contracts so that neither read the other. They are now one server, `control_mcp`, with a role for each. What is kept is the separation that matters: a role the client did not ask for has no tools. *(Correction, same day: this note first said AnythingLLM can only switch a whole MCP server on or off, so the roles were the only per-client knob. That is wrong for 1.16.2, which can switch single tools off: `anythingllm.suppressedTools` in its servers file, and toggles on its MCP page. The roles still matter for clients without such a switch (Claude Desktop, an IDE) and because a tool that is not listed cannot be switched back on by mistake; the bridge's `BRIDGE_ALLOW` is global.)* **Only `chat` is on by default**, because a scheduled job runs a prompt as the agent, unattended: adding one is a way to plant an instruction that runs later.
- **Why merge:** the two shared a client, the env variables and the developer key, and repeated the same server skeleton and error wrapper. Together they had 11 tools and AnythingLLM's MCP page warns above 10. `schedule` is now one tool with an `action` (list, add, update, delete), as the sandbox's tools are, so both roles together are 8.
- **One error type.** `BridgeError` replaces six exception classes (`McpError`, `UnavailableError`, `UnauthorizedError`, `ToolkitRefusedError`, `NotFoundError`, `InvalidInputError`). Nothing caught them apart; each carried a message to the agent. The cost is in the tests: where one used to name the class it now names the message, and `test_chats.py` and `test_jobs.py` match on it. `ToolkitApi`, the Protocol with one implementer, is gone: `Chats` and `Jobs` take the `Bridge` client, and tests put a mock transport under it.
- **The bridge's `{"error": ...}` is unwrapped,** so the agent reads `403: the bridge doesn't pass GET /x`, not the JSON around it (the first real run showed the JSON).
- **`pytest-asyncio` is back,** with `asyncio_mode = "auto"`: the hello skeleton could do without it, about sixty async tests cannot.
- **Names changed with the move,** as the bridge section above said they must: `ANYTHINGLLM_TOOLKIT_URL` is `ANYTHINGLLM_BRIDGE_URL`, `toolkit_client` is `control_mcp.bridge`, and the bridge's `install` writes one `control.env` where it wrote `chat.env` and `schedule.env` (nothing is installed from before, so there is nothing to migrate). The bridge's tests were changed for it; they ran here only as far as `tsc` and the install tests compiled with esbuild on Node 20, since `tools/check bridge` needs Node 22.18 and npm, which this machine lacked.
- **Tests:** the unit tests run against a fake AnythingLLM under the real client. `test_contract.py` checks every route a tool calls against `contract/default-allow.txt`, with a copy of the bridge's matching rules that has a negative test of its own (removing the `DELETE /workspace/*` rule from the list makes it fail, which was tried). `tools/e2e` runs the same tools against a real AnythingLLM 1.16.2 and the built bridge. The old stand-in e2e scripts (about 190 lines) were not ported.
- **Left in `anythingllm-mcp`:** `memory_mcp` (not a control: its own SQLite store and embedding model, and the `memory` skill replaces it), `sandbox_mcp` (podman, an egress proxy, its own permission model) and `deploy_mcp` (an installer; the bridge's `install` and the control server's `install` replace it). The `hello` and `world` skeletons are gone; git has them.
- **Not tried:** a chat with real exchanges against the real AnythingLLM (the throwaway has no model); saved memories, workspace settings and the other native controls, which would be roles of this server.

## Installing the control server into AnythingLLM, from deploy_mcp's notes, 2026-10-15

- **Why it is needed:** nothing registered the control server with AnythingLLM. `deploy_mcp` (1,028 lines for four servers, two modes, a dry-run plan, a status command, a sandbox image build) did, and is not moving in. This is `anythingllm-mcp-control install | uninstall`, one module (`control_mcp/install.py`, about 260 lines with its docstrings and the two unit texts) and no new dependency.
- **Kept from deploy_mcp, because the problem is the same:** AnythingLLM runs in a container with no Python, so the server runs on the host, socket-activated by systemd (a socket unit and a service template, `Accept=yes`, stdin and stdout bound to the connection), and the container reaches the socket in its storage folder through a relay. A 0600 socket in the storage folder is better than the alternative AnythingLLM 1.16.2 does offer (an SSE or streamable HTTP server): from a pasta container the host's loopback is not reachable, so the server would have to listen on a routable address with the developer key behind it.
- **Changed, to cut bloat:**
  - the relay is a `node -e` one-liner inside the entry, so there is no `bridge.js` to ship, copy or find again (it was also easy to confuse with this repository's bridge);
  - the unit is `ExecStart=<the python that ran install> -m control_mcp`, so there is no wheel to build, no `uv tool install` and no folder of installed commands, and the units always run the checkout's code;
  - the unit texts are two f-strings, not template files with placeholders;
  - one server, so one name, `control`, for the entry, units, env file and socket, and no per-server loops;
  - no Host port and Action classes: the steps are done where they are written, and what the tests need replaced is one `Machine` dataclass (environment, home, the command runner, python);
  - no mode auto-detection by inspecting running containers: default is container where `systemctl --user` answers, else native, and `--native` says so outright;
  - no dry-run, status or secret masking: `install` prints what it did, and the README points at `systemctl --user status` and the servers file;
  - the storage defaults to the bridge's `ANYTHINGLLM_STORAGE`, so after `anythingllm-bridge install` it takes no arguments (deploy_mcp read the old toolkit's settings for this).
- **Ownership of an entry** is decided by what it starts (the path of the control server's file): a `control` entry that is not ours stops `install` with a message, where deploy_mcp skipped it. The servers file is written in place, not by rename, because it belongs to AnythingLLM's user and group. A reinstall keeps the `anythingllm` block AnythingLLM keeps in our entry (`suppressedTools`, `autoStart`: set from its MCP page), since replacing the whole entry would have reset them. Marking our entries with a key of our own under `anythingllm` was not done: nothing shows that AnythingLLM keeps unknown keys there.
- **Tested:** the unit tests cover the texts, the merge and the idempotence with a recording `systemctl`. `tools/e2e` (podman) runs `install --no-start` into the storage of the throwaway container, started with `--userns=keep-id:uid=1000,gid=1000` so the container's user is the host user and the socket is reachable at 0600, with `systemd-socket-activate --accept --inetd` standing in for the two units, then makes AnythingLLM reload its MCP servers and lists `control` running with its tools. Removing the listener makes that test fail (tried). The real `systemctl enable --now` was **not** run: it would put units into the user's systemd.
- **Not carried over:** the sandbox image build, memory and sandbox themselves, Windows and macOS (the old command's native mode named `.exe` files; untested there too), and retiring the old `anythingllm-mcp-chat` and `-schedule` units, which the README says how to do with the old command.

## Portable to macOS and Windows: what the pinned image says, 2026-10-15

- **Node in `mintplexlabs/anythingllm:1.16` (1.16.2) is 18.20.8,** so anything AnythingLLM runs (the skills, and from now on the control server) targets `node18`. The bridge's `upstream.mts` uses `AbortSignal.any` (Node 20.3), so a copy shared with the control server needs a fallback.
- **A stdio MCP server gets AnythingLLM's own environment.** `server/utils/MCP/hypervisor/index.js` builds the child's `env` from `patchShellEnvironmentPath()` (`server/utils/helpers/shell.js`), which returns `process.env` after `fix-path` (and `process.env` as it is on Windows), and the entry's `env` goes over it. So `AUTH_TOKEN`, `SERVER_PORT` and `STORAGE_DIR` reach the control server without any `.env` lookup, in a container and on Desktop alike, and the servers file holds no secret.
- **AnythingLLM listens on `SERVER_PORT`, else 3001** (`server/index.js`), inside the container as on the host.
- **The servers file accepts stdio and HTTP entries:** `command`/`args`/`env`, or `url` with `type` `sse`, `streamable` or `http` and optional `headers` (`streamableHttp` is refused). The stdio entry is enough here, because the image has `node`: the control server can run inside AnythingLLM, with no host service, socket or relay.
- **Desktop storage** (docs.anythingllm.com, installation-desktop/storage): `%APPDATA%\anythingllm-desktop\storage` on Windows, `~/Library/Application Support/anythingllm-desktop/storage` on macOS, `~/.config/anythingllm-desktop/storage` on Linux. Desktop has no password or multi-user mode.
- **Not checked:** Desktop's port (taken to be 3001 as well), and Desktop itself on any OS.
- **Settings live in each OS's own folder** (`packages/shared/paths.mts`): `~/.config` or an absolute `$XDG_CONFIG_HOME` on Linux, `~/Library/Application Support` on macOS, `%APPDATA%` on Windows. The functions take the platform, the environment and the home folder as arguments, so the tests check all three layouts on any OS. On Linux nothing moves unless `XDG_CONFIG_HOME` is set, and nothing is installed anywhere else to migrate. The mode-600 checks are skipped on Windows, which has no modes; `%APPDATA%` is the user's own.

## The control server in TypeScript, run by AnythingLLM itself, 2026-10-15

- **Why:** the Python server needed a host Python 3.13 with uv, a systemd socket unit and a relay into the container, so it ran only on Linux with systemd. The stock image has Node 18 and starts stdio servers itself with its own environment (above), so a bundle in the storage folder runs wherever AnythingLLM does, with no host service, socket or developer key.
- **`packages/control`**, one file `control/dist/control.cjs` (about 30 KB) for Node 18. A port of `packages/mcp`'s control server: the same roles (`chat` by default, `schedule` opt-in), the same eight tools and instructions, the same two-call `apply`, the refused identical add, the read-back after a clear or delete. Its tests are the Python ones, ported (56 with the protocol's and the stdio test's).
- **It calls AnythingLLM directly, not through the bridge.** It logs in with `AUTH_TOKEN` from its environment and reaches AnythingLLM at `127.0.0.1:$SERVER_PORT`, both of which AnythingLLM hands it. The bridge's AnythingLLM client (`upstream.mts`, with `errors.mts` and `envfile.mts`) moved to `packages/shared/` for it; its password now comes from an .env file (the bridge) or any other source (the control server), and its errors say which. BRIDGE_ALLOW does not apply: the server calls only its own fixed routes.
- **No MCP SDK.** The TypeScript SDK brings about seventeen packages (express, hono, ajv...) for what a stdio server of tools uses: newline-delimited JSON-RPC and four methods (`initialize`, `ping`, `tools/list`, `tools/call`). `control/src/mcp.mts` is those, about 150 lines, with a check of the arguments against each tool's schema (the subset the tools use). It answers the protocol version the client asks for when it is one of 2024-11-05 to 2025-11-25, else the newest. The cost is following the protocol by hand if a later version changes what a tool server must do.
- **Tried against the real 1.16.2:** the bundle run with the container's Node 18 answered initialize and the chat and schedule tools, logged in with the container's `AUTH_TOKEN`; and with a `{"command": "node", "args": ["/app/server/storage/anythingllm-suite/control.cjs"]}` entry in the servers file, `force-reload` started it and listed it running with its eight tools, its process holding `AUTH_TOKEN`, `SERVER_PORT` and `STORAGE_DIR`. Not tried: a call through AnythingLLM's agent (the throwaway has no model), Desktop.
- **`packages/mcp` stays until `install` writes the new entry,** since the bridge's install still makes the developer key and `control.env` the Python server reads.

## One installer, and the Python side retired, 2026-10-15

## The library skill's groundwork: shared fence, net and vault, static files, QuickJS, 2026-10-15

- **Plan:** a `library-lean` skill (the user's own API toolkits: research a service's API, ask for its key, save small JavaScript functions, run them on request or on a schedule) and a rebuilt `browser-lean` (co-browsing, research, logins), both in TypeScript, sharing one instance-wide vault. This is phase 0: what both need, and the measurements that decide the engine. See [skills/library](skills/library/README.md).
- **`packages/shared/` gains what both skills use,** ported from the lean browser skill: `fence.mts` (public addresses only; the allow-list is `FENCE_ALLOW`), `net.mts` (the request a skill sends itself, fenced at its own lookup; new: an abort signal, so a stopped run drops its request), `vault.mts` (one encrypted file for the instance, `<storage>/vault-lean/vault.json`), `static.mts` (a skill's static files, overridden on the instance) and `anythingllm.mts` (the storage folder; requiring AnythingLLM's server modules, from `ANYTHINGLLM_SERVER_DIR` in tests; `perProcess` and `serial`, state and a queue kept on `globalThis`, since AnythingLLM loads a skill's `handler.js` afresh for each agent run). Memory now uses `anythingllm.mts` too, so its tests' `MEMORY_LEAN_SERVER_DIR` became `ANYTHINGLLM_SERVER_DIR`. The fence's address ranges are a `net.BlockList`, and the bridge's pairing link asks the fence whether a host is private, so there is one list of private ranges, not two that had drifted. The fenced requests keep their connections a few seconds (one pool per allow-list), so a function paging through an API doesn't open one per page.
- **The vault is written by two skills and by scheduled jobs, which AnythingLLM runs in a child process** (`jobs/run-scheduled-job.js`), so `update()` queues changes in one process (`serial`, shared by every bundled copy) and takes a lock folder beside the file across processes, re-reading the file inside it. A change is synchronous, so the lock is held for milliseconds: what needs the network (an OAuth token's renewal) is done before, and the change checks that what it read is still there. A lock older than 10 s is a dead process's and is broken. The test runs two processes making 25 changes each at once: all 50 land; with the lock taken out, 10 to 16 were lost in three runs. The lean vault was one file per workspace with no lock; its files are imported in phase 1.
- **A skill's `static/` folder is inlined into its `handler.js`** (`build.mjs` passes it as `STATIC_FILES`, an esbuild `define`, as the installer's `PAYLOAD` is), so a skill still ships two text files, which the Hub's upload (top-level text files only) and install's text payload both need. At run time, a file at the same path under `<storage>/<hubId>/static/` wins: guides, snippets and pages can be tuned on the live instance without a rebuild, and a reinstall doesn't undo it. The guide names a tuned file when it reads it. Tests check the guide's topic list against its files and that every snippet compiles. Only text and code that runs inside QuickJS is static; what touches secrets or the network stays in TypeScript.
- **One bundled dependency: QuickJS.** "No dependencies shipped" becomes "nothing installed beside a part"; `library` bundles `quickjs-emscripten-core` and `@jitl/quickjs-singlefile-cjs-release-sync`, pinned at 0.32.0. `build.mjs`'s `VENDORED` names the folders a skill may bundle, so the boundary check still fails any other package (`build.test.mts`). Why QuickJS and not `node:vm`, a container or steps: [skills/library](skills/library/README.md).
- **Measured** with a bundled spike on the image's Node 18.20.8: the bundle is 910 KB of ASCII (the wasm is base64 inside the JavaScript); the module compiles in 33 ms; re-requiring the bundle, as AnythingLLM does for each agent run, takes 12 to 15 ms.
- **AnythingLLM gives a skill no time limit.** The 60 s the sandbox server's notes speak of is the MCP SDK's default request timeout (`DEFAULT_REQUEST_TIMEOUT_MSEC`), which applies to MCP servers; neither `utils/agents/imported.js` nor aibitat limits a skill's call. A scheduled job has its own, `SCHEDULED_JOB_TIMEOUT_MS` (5 minutes by default), and a chat through the bridge has the bridge's 120 s.
- **A scheduled job names an imported skill `@@<hubId>`** (`models/scheduledJob.js`, `availableTools`), and an MCP server `@@mcp_<name>`; the control server's `TOOL_ID` refuses `@`, so a job can't be given the library through `schedule` until phase 2 changes it.

## The library skill's core, in chat, 2026-10-15

## The Library page and OAuth sign-ins, 2026-10-15

- **Chosen before unattended runs** (with the user): a key could only be given on AnythingLLM's question card, which the AnywhereLLM Lite app doesn't show, and the services without keys to paste (mail, calendars, office suites) need OAuth.

The test with a provider that rotates refresh tokens failed the second of two requests at once before the one-renewal rule.
- **One lock for small shared files:** the vault's lock folder moved to `shared/atomic.mts` (`locked`, and `updateJson` for a JSON file), and `page.json` (the page's token, secret and the agent's requests) is changed under it, briefly, after the events are applied.
- **`ANYTHINGLLM_URL`** is the skill's setting (AnythingLLM's Agent Skills page): with it the page's link works outside AnythingLLM's own chat and sign-ins come straight back.

## Runs that outlast the chat, and scheduled jobs, 2026-10-16

- **A run is recorded as `running` when it starts,** with its process and its deadline, and again when it ends; the runs going in a process are kept on `globalThis` (`store.live`), with their stop signal, since AnythingLLM loads `handler.js` afresh for each agent run and a run outlives one. A run read as `running` whose process is gone (a restart; a job's child killed at its timeout), or that is a minute past its deadline, is `interrupted`, and kept so.
- **A chat waits 40 s for a run** (`LIBRARY_WAIT_MS`), then answers with the run's id and leaves it going in AnythingLLM's process; a run may now take 10 minutes (`LIBRARY_RUN_MS`, was 3), since a long one no longer holds the chat. `run` with `run_id` waits for it again, and `stop: true` stops it. When it ends, AnythingLLM's own web push (`utils/PushNotifications`, `"primary"` or the user's id) tells the user, the page's state is written again, and the next `library` or `run` answer in a chat starts with it. "Not shown yet" is a marker file per run (`library-lean/unseen/<id>`, so a chat and a job's process never write the same file), made as every run begins and removed by the answer that shows how it ended; a job's run that doesn't end well keeps it, for the next chat, since AnythingLLM's own report of a job is its answer, and an interrupted run keeps it with no special case.
- **A scheduled job runs in a child process AnythingLLM forks for it** (bree, `jobs/run-scheduled-job.js`), with `invocation.workspace` null, the tools the job names and no others, and tool approval granted; the child races the agent against `SCHEDULED_JOB_TIMEOUT_MS` (5 minutes) and exits. So a job's run never goes to the background, and gets only the job's time left less 30 s for the agent's report: the child's `process.uptime()` is the job's age. Under 10 s left, a run is refused.
- **Scheduling is AnythingLLM's own:** the built-in `create-scheduled-job` tool (local time, converted with the browser's time zone; asks the user's approval in the chat; single-user mode only) with `tools: ["@@library-lean"]`, which its catalog lists (checked in the 1.16 image). The guide's `schedules` topic gives the prompt: run the function, report in a few lines. The control server's `schedule` takes `@@` ids now (`TOOL_ID`).
- **A run's script goes no further once its outcome is decided** (`sandbox.ts` closes the gate as the deadline or a stop wins the race, not later as it frees the runtime): a `kit.sleep` the stop rejected used to run the script on in between, and QuickJS aborted (`list_empty(&rt->gc_obj_list)`).
- **Shared now:** `#shared/anythingllm` has `jobTimeLeft()` (the forked job process's own budget) and `push()`/`pushTo()` (AnythingLLM's web push, for the browser skill too); `#shared/answer` has `flag()`, which memory used alone. A background run keeps only the page's address and whom to push to, not the agent that started it.
- **Tried in the real image:** `tests/e2e/inside.js` runs a function in a forked child as AnythingLLM forks a job's, and kills another mid-run: the next chat's `library` starts with it, interrupted. Not tried: a real job with a model, and a push to a real browser (the live instance has no subscription until the user switches notifications on).

## The vault's key outside the storage, and the browser's cookies in the vault, 2026-10-16

- **Why:** the vault's key was derived from `SIG_KEY` and `SIG_SALT`, which sit in AnythingLLM's `.env` in the same storage folder, so anyone who could read the storage, or a backup of it, could open the vault. And each workspace's Chrome profile kept its cookies in the storage, protected only by Chrome's fixed key on Linux. - **`VAULT_KEY_FILE`** (`shared/vault.mts`): a file outside the storage holding the key (32 bytes, base64). A vault opened with an earlier key (derived, or `vault.key` beside it) is sealed again under the file's, once, in the background. It must be in AnythingLLM's environment, not its `.env`: AnythingLLM's `dumpENV` (`utils/helpers/updateENV.js`) writes the `.env` again with only the keys it knows. A missing or wrong key file is refused in words; with the variable lost after the move, the error says so.
- **Cookies in the vault** (`skills/browser/src/sessions.ts`): Chrome runs with a profile in a temporary folder, removed when it closes (in the background and with retries: removing it as Chrome closes raced with Chrome's last writes, and a throw from that event handler would have taken AnythingLLM down, which the e2e found). The profiles kept in the storage before are removed at the next launch.

## The browser's own Puppeteer, and the pages' key from install, 2026-10-18

Both take an AnythingLLM internal out of the skills, by the suite's rule (supported surfaces first, internals only where nothing supported exists).

- **The browser bundles `puppeteer-core`** (pinned at 24.43.1, the newest for Node 18, which the image runs), the second entry in `build.mjs`'s `VENDORED`. It used to require the collector's Puppeteer (21.5.2) from `/app/collector/node_modules/puppeteer`, a path only the Docker image has, at whatever version AnythingLLM ships. Bundled whole, Puppeteer was 4.6 MB, three quarters of it the code that downloads browsers (proxy agents, a PAC interpreter, zip and tar, a CLI) and WebDriver BiDi; `build.mjs`'s `STUBBED` bundles those modules as empty ones, so the skill is 2.1 MB (it was 140 KB). A pattern that matches nothing fails the build, so a Puppeteer update that moves a stubbed module is caught there. Puppeteer is required at the first launch and kept per process, not evaluated again by each load of the skill. Not done: keeping it as text and compiling it once per process, which would spare each load of the skill parsing it (about 10 ms on Node 22).
- **Chrome is found, not assumed** (`browser.ts` `chrome()`): `BROWSER_LEAN_CHROME`, else the newest Chrome Puppeteer downloaded (`PUPPETEER_CACHE_DIR`, else `~/.cache/puppeteer`: the image's 119 is there, for the collector), else `/usr/bin`'s Chrome or Chromium. Linux paths only, by the suite's direction; macOS and Windows would add theirs. `headless: true` is Chrome's new headless now (`"new"` was the old Puppeteer's word for it).
- **The pages' key comes from install** (`install --page-key brx-...`, kept in `<storage>/anythingllm-suite/page-key`, mode 600), the user's choice of the four ways offered. Each skill used to make its own through `models/browserExtensionApiKey` (`validate`, `create`) and keep it beside its data, making a new one when it was revoked. Now one key serves every skill's pages, made by the user in Settings > Browser Extension; a missing key is refused in words that say how to set it, and `health` asks AnythingLLM with the browser extension's own check (`GET /api/browser-extension/check`). Install asks for it, and health checks it, only when a skill with pages is in the storage: `build.mjs` marks the skills that bundle `shared/pages` (apps, browser, library; not notebook).
